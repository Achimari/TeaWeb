# The Tea Party

One screen, one object: an original, graffiti-painted 3D cobalt teapot and its cup on a light gallery floor, with loud type around it. Scroll or drag to turn the teapot. Three parts of it are doors:

- **The spout** opens the **tea timer**: one timer shared by everyone on the site. Presets (green 2 min, oolong 3, black 4, herbal 5) or a custom time up to an hour.
- **The pot** opens **Join the line**: its lid lifts and tips open as the panel appears. One shared line for everyone; a display name only, no account, no password. You see your place and can leave.
- **The cup** opens **the first five**: the first five people in yesterday's line, with the date and their order.

Built with Next.js App Router, TypeScript, three.js, Zod, PostgreSQL and Prisma ORM 7.

For a hosted release, follow [DEPLOY.md](DEPLOY.md).

## Run locally

You need Node.js 24 (see `.nvmrc`) and PostgreSQL 14 or newer. With Docker, `npm run db:up` starts PostgreSQL 17 on `127.0.0.1:5433` with the credentials in `.env.example`.

```bash
npm install                 # also generates Prisma Client (postinstall: prisma generate)
cp .env.example .env        # DATABASE_URL, BUSINESS_TIMEZONE, TEST_DATABASE_URL
npm run db:up               # optional: PostgreSQL in Docker
npm run db:migrate          # prisma migrate deploy: creates the tables
npm run dev
```

Open http://localhost:3000. Open a second browser (or a private window) to be a second guest: both see the same line and the same timer, live.

There is no offline or browser-only mode. If the database can't be reached, the page says so plainly and joining and the timer are disabled until it is back.

## The object

- `public/models/teapot.glb` (≈ 1.3 MB, meshopt-compressed) is generated by `scripts/build-teapot.mjs`, its editable source. Change shapes, glazes or proportions there and run `node scripts/build-teapot.mjs`.
- Cream and vermilion street-art prints are curved over the model at runtime by `src/lib/teapot-art.ts`: a hand-drawn "tea" tag, a worn "ЧАЙ" stencil, and smaller eyes, numbers, arrows, drips, strokes, and Cyrillic fragments scattered at irregular heights and angles. The body profile lives in `src/lib/body-profile.mjs` so the marks and exported clay share one shape source.
- The script builds one abstract sculpture, in a single satin cobalt glaze lit by broad soft light:
  - a smooth, full, low body whose rim turns over into a finished cream interior with tea inside
  - a separate lid assembly (`Lid`: a domed lid with a skirt that drops inside the opening, a cream-glazed underside, and a cream knob), seated on the rim with a hairline gap
  - one clean tapering spout with a rounded lip
  - one slim oval handle blended into the body as a single continuous cobalt surface, with no overlapping shell at either attachment
  - a round, handleless cup with a cream interior and tea
- The script refuses to build if the handle rises into the lid's path or if the spout or handle could hit the cup as the pot turns.
- Named nodes are the interaction contract: `Spout*` → timer, `Cup*` → first five, everything else in `Teapot` (body, lid, knob, handle) → line. `HitSpout` and `HitSpoutTip` are invisible, deliberately fat hit volumes, so the thin spout is easy to click from any angle. `SpoutLip`, `KnobTop` and `CupRim` mark where the captions point.

### The lid

- The lid's shape and its single path live in `src/lib/lid.ts`, shared by the model script, the page and the tests. It lifts straight up until the skirt is clear of the opening, then tips back over its far edge and settles to lean on the rim. Closing runs the same path backwards.
- It tips over the edge toward the viewer's back left, chosen at the moment it starts to open but never over the spout or the handle (the hinge stays within 40° of the pot's sides). So the open lid is seen in profile, the interior faces the viewer, and the lid never stands above another part, at any turn of the pot.
- `tests/lid.test.ts` checks every point of the lid along the whole path stays inside the opening below the rim and clear of the handle.
- The motion is a critically damped spring: no bounce, it can be reversed at any moment from wherever it is, and it lands exactly. Switching to another part mid-way closes the lid from where it is. With reduced motion the lid is simply open.

## Interaction

- **Turn:**
  - The mouse wheel or trackpad over the page turns the teapot through a full 360°, and nothing scrolls. A short ease smooths coarse wheel notches; large input is speed-limited so one frame cannot jump most of a turn, then motion stops exactly.
  - Dragging or swiping turns it 1:1. Let go while moving and it coasts and slows to a stop; a touch catches it.
  - With the turntable focused, Left/Right turn it in 15° steps and Home faces it forward.
  - With reduced motion, turns apply instantly and nothing coasts.
- **Framing:** `src/lib/framing.ts` finds a single camera frame that contains the full 360° turn and the fixed cup. The camera stays still during rotation, then refits when the lid, panel or viewport changes. The free area is measured from the artwork's type itself (the `.say` blocks, tilts included), so large text never overlaps the pot. On wide screens two arrangements are framed, the set between the top and bottom bands of type or beside the left-hand type, and the one that shows the set larger wins.
- **Choose a part:** click or tap the part itself (raycast against the model, so it works at every angle and while the lid moves). Or use its callout: each is a real button joined to its part by a short hairline. A callout stays within 56px of its part (`src/lib/callouts.ts`), taking a clear spot beside it, away from the sculpture, the artwork's type and any open panel. Placement has no memory, so closing a panel restores exactly the callouts from before it opened; callouts step aside while the lid or framing glides and return placed for the still scene. Callouts clear from view while the teapot turns and fade back in at their settled anchors, so placement changes do not look like jumps. Where space is tight, a callout with a badge stacks into a narrower block. One whose part has turned behind the pot dims. Callouts work by keyboard and screen reader.
- **Panels:** one quiet card at a time, the same size for every part so nothing jumps; a bottom sheet on phones. When a panel opens the set glides into the space that is left (beside the card, or above the sheet on phones) instead of being covered. Focus moves into the panel, and Escape closes it and returns focus to the part's callout.
- **Fit:** at normal desktop and phone sizes the page is one screen with no scrolling. At high zoom, with large text or on very short screens the page scrolls, and the wheel then scrolls the page rather than the teapot.

### The shared tea timer

- There is **one timer for the whole site**, kept in the database (a single row). Anyone can start it; while it runs, every open page shows the same tea and the same countdown, and anyone can stop it.
- **Races:** a start only succeeds while the timer is idle or finished; if two people start at once, exactly one wins and the other gets the running timer back ("Someone else put the pot on first"). Every start and stop changes the timer's `version`, and a Stop names the version it saw, so a Stop pressed on a screen that hadn't caught up yet cannot end a newer timer.
- **Clocks:** the deadline is set by the server. Each page measures how far its own clock is from the server's (from the middle of the request) and counts down to the server deadline, so reloads, sleeping tabs and devices with wrong clocks all show the same time. At the deadline everyone sees **Ready** until someone clears it or starts the next pot.
- The spout's callout shows the time left, or **Ready**, with the panel closed too.
- Notifications are optional and belong to each device: **Notify me on this device when it’s ready** asks for permission only when pressed, and the choice is remembered on that device only. A notification can only appear while the page is open, possibly in a background tab; there is no push service.

## The shared line

- **Identity:** joining issues a random 256-bit token in an **HttpOnly, SameSite=Lax cookie** (Secure in production). The database stores only its SHA-256 hash; no response ever contains the token or the hash. Each browser or device is its own guest.
- **One place per guest per day:** a unique `(guest_key, business_date)` key enforces it, so a double submit, a retry or a second tab keeps the first place and name. Joins take a short advisory lock, so the daily capacity (500, `LINE_CAPACITY`) holds even when the last places are raced for. Order is first come, first served by join time, then insertion order.
- **Leaving** uses the key from the caller's own cookie, never the request body, so nobody can remove someone else.
- **Validation:** display names are 2–24 characters (letters in any script, numbers, spaces and `.-'’_`), with no markup or control characters, checked in the API and again by database constraints. Timer labels come from a fixed list, never free text.
- **Live updates without polling:** every write runs `pg_notify('tea_changes', …)`. Each server process keeps one `LISTEN` connection and streams a bare "changed" event to open pages over Server-Sent Events (`/api/events`); pages then fetch `/api/state` once. So the roster, the total and your place badge on the pot update within a moment of anyone joining or leaving, even with the panel closed. An idle page makes no requests at all; a slow safety-net check runs once a minute, and on returning to the tab.
- **Abuse limits:** joins and leaves (20 per 10 minutes) and timer starts and stops (30 per 10 minutes) are counted per client address in the database, so every server process shares the count. Reads are limited per process.

### Daily archive and reset

- The business day is the calendar date in **Europe/Riga** (`BUSINESS_TIMEZONE`), daylight-saving time included; timestamps are stored in UTC.
- Closing a day archives its first five into `daily_archive` and clears it, in one transaction, under an advisory lock, with a primary key on `(business_date, position)`, so concurrent or repeated runs can neither erase nor duplicate results.
- It runs on a schedule inside the server (every five minutes, from `src/instrumentation.ts`), and at the start of every line read and write, so a missed run changes nothing.
- If fewer than five people joined, only they are archived. A day with nobody shows an honest empty state.

## Database (PostgreSQL + Prisma ORM 7)

- Schema: `prisma/schema.prisma` (four tables: `queue_entries`, `daily_archive`, `shared_timer`, `rate_limits`). Migrations: `prisma/migrations/`; rules Prisma's schema language can't express (CHECK constraints, the timer's single row) are in the migration SQL. CLI configuration: `prisma7.config.ts`.
- Prisma Client is generated into `src/generated/prisma` (not committed) by `npm install` and `npx prisma generate`, and talks to PostgreSQL through the `@prisma/adapter-pg` driver adapter. Versions are pinned: `prisma`, `@prisma/client` and `@prisma/adapter-pg` 7.10.0, `pg` 8.23.1. Two of the Prisma CLI's own dependencies (`mysql2`, `deepmerge-ts`) are pinned through `overrides` to their patched releases, the same ones Prisma 7.10.1 ships.
- Commands for this Prisma version:
  - `npx prisma migrate deploy` (`npm run db:migrate`): apply pending migrations. Use this in production.
  - `npx prisma migrate dev --name <change>` (`npm run db:migrate:dev`): after editing the schema, locally only.
  - `npx prisma generate`: regenerate the client.
- All database access is in `src/lib/server/store.ts`; the API routes are `src/app/api/{state,queue,timer,archive,events}`.

### Moving an existing Supabase line

`scripts/import-from-supabase.mjs` copies today's line and the archive from an old Supabase database into the new one. It only reads from Supabase, never changes it, and skips rows that are already there. See DEPLOY.md.

## Checks

```bash
npm test           # timer and clock offset, rotation, lid, framing, callouts, business day (DST), validation, request origin, guest tokens, and the store against PostgreSQL
npm run typecheck
npm run lint
npm run build
npm run test:e2e   # browser checks against the production build (needs the database in DATABASE_URL; run after npm run build)
```

`npm run test:e2e` (Playwright 1.63, Chromium; first time: `npx playwright install chromium`) starts the standalone server on port 3210 and checks, at 1440×900, 390×844 and 320×568: that opening and closing each panel restores the same composition (pins and callouts within 2px), through repeated cycles, panel switches, closing mid-transition, a turned pot, a resize while open, and reduced motion; no sideways scrolling; the short-phone timer sheet; panel layouts; the line visible before joining; focus never moved by other people's changes; and, with two isolated browsers, the shared line, the shared timer, a stale stop and the archive date. It clears only the rate-limit counters before a run.

`tests/store.test.ts` runs against a real PostgreSQL: it creates a throwaway database on the server in `TEST_DATABASE_URL`, applies the Prisma migrations, and drops it afterwards. It covers two guests seeing one ordered line, duplicate and concurrent joins, the capacity under a race, leaving only your own place, rollover at Riga midnight (including concurrent rollovers), the end of daylight-saving time, an empty day, simultaneous timer starts, a stale stop, Ready at the deadline, and rate limits shared across processes. CI provides PostgreSQL as a service container.

## Known limits

- Rate limits are keyed on the first `X-Forwarded-For` address. Behind Caddy (which replaces any client-sent value) that is the real visitor; exposed without such a proxy, the limits could be dodged. The daily capacity still bounds the line.
- Live updates need one long-lived connection per open page (to the Node server) and one `LISTEN` connection per server process (to PostgreSQL). A proxy that buffers responses would delay the events; pages then fall back to the once-a-minute check.
